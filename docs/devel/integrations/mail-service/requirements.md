# 独立邮件服务集成：需求目标

## 1. 当前情况

当前 AI-Nexus 通过 `VarifyService.GetVarifyCode(email)` 调用外部 gRPC 服务。外部
服务生成验证码并把明文验证码返回给 AI-Nexus，随后 AI-Nexus 将其写入
`user_verification_codes` 表。

注册、验证码登录和密码重置流程实际又从 Redis 的 `code_{email}` Key 读取验证码。
这意味着验证码生成、存储和验证的职责没有形成清晰闭环，可能依赖两个系统共享
Redis 等隐式约定。

当前协议还存在以下不足：

- 邮件服务承担了验证码生成这一业务职责；
- 无法区分“投递任务已受理”和“邮件已被供应商接受”；
- 没有请求幂等键、回调幂等键和明确状态机；
- 没有回调丢失后的对账接口；
- 没有约定重试、熔断、死信和超时语义；
- 协议中的 `Varify`、`GetVarifyCode` 存在命名错误；
- 验证码按邮箱单独存储，不能可靠隔离注册、登录和密码重置用途。

## 2. 建设目标

建设一个独立 Mail Service，并由 AI-Nexus 通过版本化 gRPC 协议调用。

AI-Nexus 负责：

- 校验邮箱、验证码用途和账号状态；
- 生成密码学安全的验证码；
- 管理验证码状态、有效期、错误次数和一次性消费；
- 实施邮箱、IP 和业务用途维度的防滥用限制；
- 接收并幂等处理邮件投递状态回调。

Mail Service 负责：

- 幂等受理邮件投递命令；
- 持久化邮件任务并异步执行；
- 管理模板、国际化和供应商适配；
- 实施超时、重试、指数退避、熔断和死信；
- 可靠回调邮件状态；
- 提供任务状态查询用于对账。

## 3. 功能需求

### 3.1 验证码生成

- 验证码必须由 AI-Nexus 使用 `crypto/rand` 生成；
- 验证码用途包括注册、密码重置和验证码登录；
- 不同用途的验证码不得互相使用；
- AI-Nexus 不持久化验证码明文，只保存带服务端密钥的 HMAC 摘要；
- 验证成功后必须原子消费，不能被并发重复使用。

### 3.2 邮件任务受理

- AI-Nexus 为每次发送生成全局唯一 `request_id`；
- Mail Service 必须以 `request_id` 作为幂等键；
- 首次受理返回 `ACCEPTED` 和 `message_id`；
- 重复请求不得创建或发送第二封邮件，应返回原 `message_id` 和 `DUPLICATE`；
- Mail Service 只有在任务已经可靠持久化后才能返回受理成功。

### 3.3 异步投递

- gRPC 请求只等待任务可靠受理，不等待 SMTP 投递完成；
- Mail Service 在后台完成排队、模板渲染和供应商调用；
- 超过 `dispatch_deadline` 的验证码邮件不得继续投递；
- 临时故障按退避策略重试，永久故障不得无意义重试；
- 重试耗尽的任务进入死信队列。

### 3.4 状态回调

- Mail Service 使用独立 `event_id` 回调 AI-Nexus；
- AI-Nexus 必须幂等处理重复回调；
- 状态事件携带单调递增的 `sequence`，避免乱序事件覆盖新状态；
- 回调失败时 Mail Service 必须重试；
- 回调重试耗尽后进入回调死信队列；
- AI-Nexus 可通过 `GetEmailStatus` 主动对账。

### 3.5 验证码激活

- AI-Nexus 在调用 Mail Service 前创建 `PENDING_DISPATCH` 记录；
- Mail Service 返回 `ACCEPTED` 只代表任务已可靠保存；
- AI-Nexus 收到第一次肯定投递状态 `PROVIDER_ACCEPTED` 或 `DELIVERED` 后，将验证码
  幂等激活为 `ACTIVE`；
- 验证码有效期从首次激活时间开始计算，后续重复或更高状态回调不得延长有效期；
- 永久投递失败时验证码进入 `DELIVERY_FAILED`，并允许用户重新申请。

## 4. 非功能需求

### 4.1 可靠性

- 系统采用“至少一次投递 + 幂等处理”，不宣称网络调用严格只发生一次；
- 邮件任务入队和状态回调分别使用持久化 Outbox；
- Mail Service 重启后未完成任务可以恢复；
- 单个供应商故障不得导致 gRPC 接入层长时间阻塞。

### 4.2 安全

- 生产环境 gRPC 使用 TLS，推荐 mTLS；
- 服务端必须校验调用方身份；
- 不得在日志、错误消息或链路标签中记录验证码；
- Mail Service 为异步发送而持久化的敏感模板变量必须加密，并在终态后及时清理；
- 请求不能携带任意 HTML 或动态回调地址；
- 错误回调不得泄露 SMTP 凭证或完整供应商响应。

### 4.3 可观测性

- 全链路关联 `request_id`、`message_id` 和 Trace ID；
- 记录受理量、发送成功率、重试量、熔断状态、死信量和回调延迟；
- 日志字段必须经过脱敏，不直接记录完整邮箱和验证码。

## 5. 非目标

- 第一阶段不建设营销邮件编排平台；
- 第一阶段不实现用户可视化邮件偏好中心；
- 第一阶段不承诺 SMTP 接受即代表最终送达用户收件箱；
- 第一阶段不允许业务服务直接传入完整 HTML；
- 本文档不规定 Mail Service 必须使用哪一种邮件供应商。

## 6. 验收标准

- 同一 `request_id` 重试不会产生重复邮件；
- `ACCEPTED` 后即使进程重启，任务仍可继续执行；
- `PROVIDER_ACCEPTED` 或 `DELIVERED` 可以将对应验证码从 `PENDING_DISPATCH`
  激活为 `ACTIVE`；
- 重复和乱序回调不会重复激活或延长验证码有效期；
- 注册验证码不能用于登录或密码重置；
- 验证码只能成功消费一次；
- 供应商临时失败会重试，永久失败不会持续重试；
- 熔断开启时任务不会丢失，恢复后可继续处理；
- 回调失败可以重试，并可通过查询接口完成对账；
- Mail Service 无需访问 AI-Nexus 的 Redis 或 MySQL。
