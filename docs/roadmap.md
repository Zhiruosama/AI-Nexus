# AI-Nexus 演进路线图

## 项目定位与边界

项目定位为：**面向多模型 AI 服务的统一接入、异步任务调度与账户计费平台**。

一个月内聚焦“充值 → AI 消费 → 失败解冻/补偿 → 退款/对账”的闭环；不扩展为完整商城，不引入 Kubernetes、注册中心或更多 Provider 来堆砌概念。

## 已完成基线

- WSL2 本地开发环境、Git SSH 身份和 Go 工具链已就绪。
- Docker Compose 提供 MySQL、Redis、RabbitMQ，三项服务健康并完成连通性验证。
- 私有 `.env` 与 `configs/config.yaml` 已从 Git 跟踪配置中分离，模板可复现本地环境。
- Postman Collection 与环境模板覆盖当前路由；应用已完成数据库、缓存、消息队列启动验证。
- `go build ./...`、`go vet ./...`、`go test ./...`、`golangci-lint run ./...` 均通过；当前仍缺少实际测试用例。

## 阶段一：可信、可运行、安全（最高优先级）

### 范围

- 完善 README、启动说明、架构图和故障排查入口。
- 修复会话与越权：HTTP JWT 校验 Redis 登录态、资源 owner 校验、模型管理 RBAC。
- 修复 WebSocket Origin、密码重置分支、RequestID、请求去重等明显问题。
- 为 JWT、密码、状态机和核心中间件新增单元测试；补充登录与任务提交集成测试。

### 验收标准

- 退出登录后的旧 JWT 无法访问受保护接口。
- 用户无法读取、取消或修改其他用户资源。
- 未授权用户不能修改模型配置。
- 核心安全规则均有自动化测试，CI 可重复执行。

## 阶段二：异步任务可靠性

### 范围

- Transactional Outbox，确保业务写入和事件发布最终一致。
- Consumer Inbox/业务唯一键幂等，CAS 状态迁移。
- TTL/死信队列实现指数退避，避免立即 requeue 风暴。
- API Server 与 Worker 拆分；为多实例 WebSocket 通知预留 Redis Pub/Sub 或通知表方案。

### 验收标准

- 重复消息不会重复创建任务或重复结算。
- 取消和完成并发时只有一个终态可以成功。
- Broker 暂时不可用不会丢失已提交任务，恢复后可补发。

## 阶段三：支付与计费闭环

### 范围

- 钱包账户、不可变账本、充值订单、支付尝试和回调事件。
- MockPaymentProvider：重复回调、乱序回调、失败回调测试。
- AI 任务预冻结，成功实扣，失败/取消释放冻结；退款/补偿单与基础对账。

### 必须守住的不变量

- 金额使用最小货币单位整数，不使用 `float`。
- 余额更新与账本流水在同一事务；流水仅追加，不修改、不删除。
- 同一支付渠道事件只能入账一次。
- 任何余额可由流水重算；任务只能结算一次。

### 验收标准

- 重复支付回调不会重复加余额。
- 余额不足时任务不会进入队列。
- 任务失败、取消、重复投递都不会造成重复扣款或冻结泄漏。

## 阶段四：可观测性与面试证据

### 范围

- Prometheus 指标、结构化日志、RequestID 贯通。
- 固定压测环境，记录命令、数据集、P50/P95/P99、错误率。
- RabbitMQ 不可用、重复投递、Worker 崩溃、重复回调的故障演练。
- CI 增加单测、集成测试、`-race`、覆盖率、漏洞扫描；整理 ADR 与面试问答。

### 验收标准

- 每项简历性能或可靠性结论均可定位到脚本、环境与原始结果。
- 核心故障场景有演练步骤和可验证结论。

## 工程决策原则

1. 先修正确性、安全性和可验证性，再增加新功能。
2. 每个阶段只交付可运行、可测试、可说明的最小闭环。
3. 设计文档、README 与简历表述必须严格对应已验证实现。
4. 不提交真实密钥、生产数据或公司内部资料；已有泄露风险的历史密钥应轮换。
5. 重要取舍以 ADR 记录：背景、方案、决定、后果与回滚方式。
